# Control-Flow Three-Address Code (Week 9)

Until now, a program's 3AC ran **straight through**: triple (0), then (1), then (2), and so on.
Control flow breaks that, since a triple can now say "continue somewhere else". Three new triple
kinds do this. They are already defined in `three_address_code.py`, and none of them computes a
value.

| Triple | Rendered as | Meaning |
|---|---|---|
| `LabelTriple(label)` | `(6) L0:` | a jump target; does nothing when reached |
| `GotoTriple(label)` | `(8) goto L1` | always continue at `label` |
| `IfFalseTriple(cond, cond_type, label)` | `(4) if_false (3) goto L0 : INT` | if `cond` is **0**, continue at `label`; otherwise fall through to the next triple |

`cond` is an ordinary operand: usually a `TripleRef` to a comparison's 0/1 result, but it may also
be a variable (`if (d)`) or a literal. `cond_type` records whether `cond` is an `INT`/`CHAR` or a
`DOUBLE`, because MIPS tests the two differently (`docs/mips_branching_reference.md` #2).

Labels are plain strings, `"L0"`, `"L1"`, and so on, handed out by `TACGenerator.new_label()`, the
**fresh-label allocator**. A label must never be issued twice within a function, or two different
jumps would land in the same place.

## Why jump on *false*?

Code is laid out in source order: the condition first, then the branch. If the condition is
**true**, execution should simply continue into the branch, so the only jump needed is the one
that skips the branch when the condition is **false**. That is why the IR has `if_false`, and
`if_true` isn't needed for `if` or `while`.

## The three translation schemes

`<cond>` stands for the triples `gen_expr(stmt.cond)` emits, and `c` for the operand it returns.

**`if (cond) then_stmt`** uses one label:
```
        <cond>
        if_false c goto Lend
        <then_stmt>
Lend:
```

**`if (cond) then_stmt else else_stmt`** uses two labels:
```
        <cond>
        if_false c goto Lelse
        <then_stmt>
        goto Lend            <- without this, the then-branch would fall into the else-branch
Lelse:
        <else_stmt>
Lend:
```

**`while (cond) body`** uses two labels:
```
Ltop:                        <- BEFORE the condition: it is re-evaluated on every iteration
        <cond>
        if_false c goto Lend
        <body>
        goto Ltop            <- the back edge, which is what makes this a loop
Lend:
```

**`{ s1 s2 ... }`** produces no triples of its own: just generate `s1`, `s2`, ... in order.

**Nesting needs no special code.** `<then_stmt>`, `<else_stmt>` and `<body>` are generated by a
recursive `gen_stmt()` call. If a branch is itself an `if` or `while`, it allocates its own fresh
labels and emits its own scheme inside the outer one. Three levels of nesting work the same way as
one.

## The label-order convention (the golden files depend on it)

> A statement allocates **all** of its labels first, in the order listed above (`Lend`; or
> `Lelse, Lend`; or `Ltop, Lend`), **before** generating its condition, branches or body.

Any consistent order gives a correct program; this one is fixed so that everyone's `.3ac` matches
the goldens. For example, the outer `if` in `tests/test13.tc` takes `L0`, and the inner `if-else`
then takes `L1, L2`:

```
(5) > a, b : cmp INT
(6) if_false (5) goto L0 : INT       <- outer if (no else): L0
(7) > b, c : cmp INT
(8) if_false (7) goto L1 : INT       <- inner if-else: L1 (else), L2 (end)
(9) x = 1
(10) goto L2
(11) L1:
(12) x = 2
(13) L2:
(14) L0:                              <- two labels in a row: both mark the same spot
```

## Why the ternary still does NOT use these triples

`c = (a > b) ? x : y` and `if (a > b) c = x; else c = y;` compute the same thing, yet the ternary
stays a single flat `SelectTriple` (Week 7). The difference is that a ternary is an **expression**:
it produces a value that some other triple consumes through a `TripleRef`. A `TripleRef` points to
one triple, and a value assembled from two jump paths has no single triple that holds it. An
`if` is a **statement**: it produces no value, so it lowers naturally to jumps. (Production
compilers lower both forms to jumps, by giving the ternary's result a named temporary that
both paths assign. That needs temporaries with names, which triples deliberately don't have.)

## Control-flow graphs (CFG)

A **basic block** is a maximal run of triples that is always executed from first to last: control
enters only at the top and leaves only at the bottom. A **CFG** has one node per basic block, and
an edge `B1 → B2` whenever control can go from the end of `B1` straight to the start of `B2`.

A block **starts** (its first triple is a *leader*) at:
1. the first triple of the function;
2. any label, since something may jump to it;
3. the triple right after a `goto` or `if_false`.

A block **ends** with an edge to:
- the jump target, for `goto` (one edge only: no fall-through);
- **both** the target and the next block, for `if_false`;
- the next block, for anything else (fall-through).

### Worked example: `tests/test10.tc`

```
(0) a = 50                     B1  (leader: first triple)
(1) b = 40
(2) flag = 0
(3) > a, b : cmp INT
(4) if_false (3) goto L0 : INT     -> B3 (false) / B2 (true, fall through)
(5) flag = 1                   B2  (leader: follows an if_false)
(6) L0:                        B3  (leader: label)
(7) PRINT flag
(8) != a, b : cmp INT
(9) if_false (8) goto L1 : INT     -> B5 (false) / B4 (true)
(10) - a, b : INT              B4  (leader: follows an if_false)
(11) a = (10)
(12) PRINT a
(13) L1:                       B5  (leader: label) -- exit
```

```
        B1
       /  \
   true    false
     |       \
    B2        |
     \        |
      ------> B3
             /  \
         true    false
           |       \
          B4        |
           \        |
            ------> B5 (exit)
```

The diamond shape **B1 → {B2, B3} → B3** is what every `if` without an `else` looks like. Before
writing any code this week, draw the CFG for `tests/test12.tc` (the `while` loop) the same way. A
`while` loop has an edge going **backwards** to an earlier block; find it, and say which triple
creates it. Week 12 builds this CFG automatically from the 3AC, and compares it with your drawing.
